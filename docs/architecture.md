# Устройство KIRO Push

Краткое описание для разработчиков и администраторов, которым нужно понимать, что именно делает плагин. Подробности запросов: [api.md](api.md).

## Таблицы

Миграция `kiro-push.0001_initial` идемпотентна (`CREATE TABLE IF NOT EXISTS`) и ничего не изменяет в таблицах Core.

| Таблица | Назначение |
| --- | --- |
| `ext_kiro_push_config`, `ext_kiro_push_meta` | настройки плагина и служебные флаги (например, «автосканирование уже запускалось») |
| `ext_kiro_push_birthdates` | даты рождения: день, месяц, год (необязателен), источник (`telegram`, `user`, `admin`), признак `locked`, статус проверки, число попыток |
| `ext_kiro_push_birthdate_audit` | аудит: кто и когда установил, получил из Telegram или удалил дату |
| `ext_kiro_push_user_attempts` | попытки самостоятельного ввода (ограничение `user_attempts_per_hour`) |
| `ext_kiro_push_backfill` | состояние единоразового сканирования Telegram (курсор, счётчики) |
| `ext_kiro_push_events` | события: вид, параметры, аудитория, время, подарок, шаблоны; удаление мягкое |
| `ext_kiro_push_plans` | какие слоты (событие, день) уже спланированы |
| `ext_kiro_push_deliveries` | доставки: статус, причина, подарок, промокод, попытки; уникальный ключ `(event_id, user_id, period_key)` |
| `ext_kiro_push_batches` | ручные запуски по `batch_id` |
| `ext_kiro_push_blocked` | пользователи, заблокировавшие бота |
| `ext_kiro_push_media` | загруженные по частям файлы для шаблонов |
| `ext_kiro_push_log` | журнал событий плагина |

## Периодическое задание `tick`

Durable job Core `tick` запускается раз в 60 секунд (таймаут 55 секунд, одна попытка). Пока `enabled = false`, он ничего не делает. За один проход:

1. **Планирование.** Для каждого включённого события, кроме `manual`, вычисляются «слоты» (день и время отправки в часовом поясе плагина, с окном догонки `catchup_hours`). Для слота выполняется один идемпотентный `INSERT ... SELECT` в `ext_kiro_push_deliveries`. Повторное планирование того же слота не чаще чем раз в 10 минут, дубли отсекает уникальный ключ.
2. **Новые пользователи и повторные проверки Telegram** (небольшие порции по 30, делят квоту Telegram с отправкой).
3. **Автосканирование**, если включён `auto_backfill` и оно ещё не запускалось.
4. **Отправка** очереди доставок в пределах отведённого бюджета времени и лимита `send_rate_per_second`.
5. **Сканирование Telegram** (backfill) на оставшееся время.

Кроме того, обработчик событий `user.registered` и `account.telegram_linked` через короткую задержку проверяет дату рождения нового пользователя (периодический проход подстраховывает, если событие пропущено). Брошенные незавершённые загрузки файлов старше суток удаляются.

## Планирование событий

* `birthday` сопоставляет месяц и день даты рождения с датой слота; 29 февраля в невисокосный год попадает на 28 февраля или 1 марта по правилу `feb29`. Смещение `offset_days` сдвигает отправку.
* `registration_anniversary` берёт пользователей, у которых совпадает месяц и день регистрации в часовом поясе плагина и прошло не меньше `min_years` лет. Календарную дату решает Python (`zoneinfo`), а не база: SQL лишь грубо отбирает кандидатов по UTC.
* `fixed_date` и `one_time` планируются по дате; `manual` создаёт доставки только по кнопке «Запустить».
* Период (`period_key`): год для ежегодных событий, дата для `one_time`, `m:<batch_id>` для ручных запусков. Один человек получает не больше одной доставки на событие и период.
* Аудитория: сегмент подписки (нет, пробная, платная), язык, тарифы (только для платных). Забанённые в Minishop пользователи исключены всегда. Параметр аудитории `skip_blocked` (по умолчанию `true`, хранится внутри JSON `audience`, миграция не нужна) дополнительно исключает заблокировавших бота: тех, у кого в Minishop `users.telegram_notifications_status = 'blocked'` (колонка определяется один раз через `information_schema`; если её нет, условие не добавляется), и тех, кто записан в `ext_kiro_push_blocked` не раньше `blocked_retry_days` дней назад. NULL, `unknown` и `enabled` не исключают никого. Условие одинаково применяется при планировании (`audience_conditions`), в пробном и настоящем ручном запуске и при повторной проверке перед отправкой.

## Конвейер доставки

Доставку берёт в работу один воркер: `UPDATE ... FOR UPDATE SKIP LOCKED` переводит строку в `sending`. Далее `process_delivery`:

1. Проверяет событие (удалено или выключено, кроме ручных запусков), пользователя (нет в базе, забанен, нет Telegram ID, заблокировал бота: проверяется только при `skip_blocked`, причина `user_blocked`) и выбирает шаблон по языку пользователя с откатом на `default_language`. Иначе доставка получает статус `skipped` с причиной.
2. Если у события есть подарок, выдаёт его (см. ниже) **до отправки**. Если подарок выдать нельзя, действует правило события: отправить текст без подарка (`text_no_gift`) или пропустить.
3. Подставляет значения в шаблон, проверяет длину (4096 знаков, 1024 для подписи к медиа), отправляет сообщение с медиа и кнопками.
4. Записывает результат: `sent`, `blocked`, `skipped`, `failed` либо возвращает в очередь.

Ошибки отправки:

* Telegram 429: учитывается `retry_after`, строка возвращается в очередь, попытка не засчитывается, остаток пачки откладывается.
* Блокировка бота: статус `blocked`, пользователь запоминается в `ext_kiro_push_blocked` (в том числе при выключенном `skip_blocked`: при следующей отправке с включённым параметром он будет пропущен).
* Прочие ошибки повторяются через `retry_minutes` до `max_send_attempts`, затем `failed`.
* Если Telegram отклонил custom emoji, сообщение отправляется ещё раз с обычными эмодзи.

## Идемпотентность

* Планирование: `ON CONFLICT (event_id, user_id, period_key) DO NOTHING`.
* Ручной запуск: `batch_id` (клиент хранит его до успеха); повтор с тем же `batch_id` ничего не отправит дважды.
* Подарок: выдаётся в отдельной транзакции и фиксируется на строке доставки (`gift_status = granted`) в том же коммите; ключ идемпотентности `push:<событие>:<пользователь>:<период>` защищает ещё и на стороне Core и kiro-wheel.
* Сообщение: если воркер начал отправку и упал (строка в `sending` дольше 10 минут и `send_started_at` заполнен), строка помечается `failed: interrupted_during_send` и **не** отправляется повторно. Дубль хуже потери.

## Подарки

Один подарок на событие. Выдаётся в одной транзакции с блокировкой строки пользователя (порядок блокировок как в Core).

| Вид | Как выдаётся |
| --- | --- |
| `days`, `traffic`, `balance` | награда Core (`rewards.grant`, владелец `kiro-push`); дни и трафик требуют активной подписки |
| `promo_discount` | персональный одноразовый промокод через `PromoCodeService.issue_code(origin="kiro-push")` со сроком `valid_days` |
| `wheel_spins` | запись в таблицы kiro-wheel (`ext_kiro_wheel_grants` с ключом идемпотентности и `ext_kiro_wheel_credits`) с учётом лимита накопления, если не задано `ignore_cap` |

Исходы: `granted`, `not_eligible` (например, нет подписки), `unavailable` (kiro-wheel не установлен), `failed`. Временные ошибки (база, панель) не фиксируются: вся доставка повторяется позже.

## Как берутся даты рождения

* **Telegram.** Метод `getChat` возвращает `birthdate`, только если пользователь открыл дату для бота. Сканирование («backfill») идёт порциями по ~45 секунд за запуск задания, со скоростью `scan_rate_per_second`, с сохраняемым курсором, учётом `retry_after` и режимом «пробный запуск» (считает долю найденных, ничего не сохраняет). Новые пользователи проверяются по событию регистрации и в периодическом проходе. Пользователи без видимой даты перепроверяются раз в `rescan_missing_days` дней, не более `rescan_max_attempts` раз.
* **Сам пользователь.** Карточка «День рождения» в настройках Mini App: день, месяц, год по желанию, обязательная галочка согласия и экран подтверждения. Попытки ограничены (`user_attempts_per_hour`). Пользователь записывает только свою строку.
* **Администратор.** Правка, удаление и импорт (до 2000 строк) в разделе для поддержки.

## Правила блокировки даты

* Любая сохранённая дата имеет `locked = true`: Telegram её не обновляет (запись обновляется только там, где даты нет, она не заблокирована и не очищена администратором), пользователь изменить её не может (`already_set`).
* Менять и удалять дату может только администратор; каждое действие пишется в `ext_kiro_push_birthdate_audit`.
* После удаления администратором строка получает статус `cleared`: пользователь может ввести дату заново, а Telegram удалённую запись не заполняет.
* Если пользователь успел ввести дату сам, результат сканирования её не перезаписывает.
